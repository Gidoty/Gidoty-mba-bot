# Profit protection v2, Part I: partial profit. Design note only. No code was written for it.

Base branch: `feature/reentry-after-protective-exit` (Part J), on the Part A to G chain. Nothing in this note changes the bot.

## Decision: stop at a design note
The request allows this when the risk is too high for the current single-slot design. I judge that it is, for these concrete reasons found in the code:

1. **A trade is one quantity and one price everywhere.** `trade.quantity` is read in 14 places in `lifecycle.py` (protective stop size, the exit loop's "how much is left", reconcile's size check, `_finalize`'s fee and price lookups, the Spot "can I still protect this" test). `exit_price`, `pnl`, `exit_fee_quote` and `funding_quote` are single columns. Two exits on one trade means every one of those reads must learn about a remaining quantity, and the realised result becomes a sum of two legs. A bug in any of them is a wrong size on a real order or a wrong P&L figure.
2. **The reconciler would see a healthy partial as an incident.** `reconcile_trade` compares the exchange position with `trade.quantity` (line 815 and 876: `remaining = min(abs(signed), trade.quantity)`, `expected = max(trade.quantity - sold, 0)`). After a partial exit the position is half of `trade.quantity`; today that reads as a position that does not match, and the trade would go to `attention` (new trades on hold). The reconciler needs a new state ("partially exited, remaining Q") and a rule for every combination of {partial order filled / not filled} x {stop updated / not updated}.
3. **The stop must never be larger than the position and the position must never be without a stop.** On Futures the protective stop is `closePosition` (sized by Binance to the whole position), so a partial exit shrinks it automatically; the `reduceOnly` fallback carries an explicit size and would then be too large (Binance rejects or trims it, UNVERIFIED which). On Spot the stop is a quantity-locked order: the partial sell cannot even be placed while the stop holds all the coins (the same reason the Spot trail already fails with `InsufficientFunds` in the fake, UNVERIFIED on real Binance Spot). A safe Spot partial would have to cancel the stop first, which leaves the whole position unprotected for the duration of two calls. That breaks the rule this bot is built around.
4. **The restart window.** Between "partial order filled" and "stop updated" a restart must finish the job. That needs a durable intent record (what was sold, what stop is owed), which is a new table or new columns and a new recovery path in `recover_once`. The existing idempotent client-order-id scheme (`client_id(trade, role, attempt)`) would need a new role and a new attempt counter.
5. **Minimum order size.** Futures: a half position can fall below the symbol's minimum notional or step (a small account at 0.001 BTC cannot sell 0.0005 BTC). The rule would have to skip silently, which makes the measured and the live behaviour differ. Spot: the remaining quantity after rounding to the lot step can leave dust that cannot be sold or protected.
6. **Evidence first.** The sealed test (Part H) measures what a partial exit would earn in a simulation. If it pays after the extra costs, the design below is the starting point. If not, none of the above risk is worth taking.

## What a safe version would need (so this is not a "no" with no plan)
Futures only, first. Not Spot.
- Schema: `trades.partial_quantity`, `partial_exit_price`, `partial_fee_quote`, `partial_at`, `partial_stage` (none / ordered / filled / stop_updated), and `quantity_remaining`. One additive migration.
- Order of operations, each step durable before the next, all idempotent by client order id: (1) record intent `ordered` with the quantity; (2) place a reduce-only market order for the fraction, rounded DOWN to the lot step, skipped if below the minimum notional (no partial, the trade stays whole); (3) read the fill back; (4) `closePosition` stops resize themselves, but place and verify a new protective stop for `quantity_remaining` FIRST, then cancel the old one (same rule as `move_stop`), then move the stop to entry plus the cost buffer as part of the same step; (5) record `stop_updated`.
- A rejected partial order: the trade is untouched and still fully protected (the original stop is never cancelled before the partial fills). The failure is logged and the rule does not retry that trade.
- Restart between (3) and (4): `recover_once` sees `partial_stage = filled` with a position equal to `quantity_remaining` and finishes (4). Between (2) and (3): it looks up the order by client id (it is deterministic) and adopts its state.
- P&L and fees: the trade's realised P&L is the sum of the two legs, the exit fee is the sum of the two exit fills' fees, `exit_price` is the quantity-weighted average. Reports use those; the extra leg costs a full fee and slippage on its own notional.
- Spot: not supported until a stop order that survives a partial sell is confirmed on real Binance Spot (OCO or a stop that adjusts). UNVERIFIED today.

## What I did instead
Part H simulates partial profit (close half at +1.5 R, move the stop on the rest to entry plus the cost buffer, trail the rest) with every leg's fee and slippage counted, so the owner can see what it would be worth before anyone writes the live code.
