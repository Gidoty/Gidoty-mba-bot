# Account-wide daily loss limit (the customer's dollar amount) and Futures leverage ceiling

Status: both ship OFF. With `ACCOUNT_DAILY_LOSS_LIMIT` unset (default) and `FUTURES_MAX_LEVERAGE=0` (default) the cycle reads and writes nothing here. Updated 18 Nov 2026: the daily limit is now the customer's own amount in USDT; the old percent variable `ACCOUNT_DAILY_LOSS_PCT` is no longer read by any code. CLAUDE-RUN: tests pass in the sandbox against a FAKE exchange. Nothing is deployed, no migration has been run, no order has been placed.

## 1. Daily loss limit (`ACCOUNT_DAILY_LOSS_LIMIT`, `ACCOUNT_DAY_TIMEZONE`, `trading_accounts.daily_loss_limit_usd`)

For a LIVE account (paper accounts are not affected). When the account's value is the customer's amount (USDT) or more below the value it started the local day with, no NEW entry is opened until the end of that day. The switch `ACCOUNT_DAILY_LOSS_LIMIT` (default off) turns the enforcement on for every account; the amount, its validation and the one-time default exist whether or not the switch is on.

### The amount (`daily_limit.py`)
* **Required before live trading.** `POST /api/account/enable-live-trading` and `POST /api/account/start-bot` answer 409 until the account has an amount (checked after the open-trade check, before any write). The customer sets it with `PATCH /api/account` (`daily_loss_limit_usd`), on the Risk tab of Bot Settings.
* **Validation:** a number above 0 and below the dollar level of the total stop (`risk_limits.TOTAL_STOP_PCT`, 50 percent, of the reference value: the total stop's reference, else the last stored value, else the trading capital), so the daily limit can never be higher than the total stop. With no reference known yet only "above 0" can be checked.
* **Suggestion and percent:** the API returns `daily_loss_limit_suggested_usd` (5 percent of that reference value) and `daily_loss_limit_pct` (the amount as a percent of it). The customer types the number; nothing is filled in for them.
* **Lowering applies at once. Raising starts at the next midnight in `ACCOUNT_DAY_TIMEZONE`.** A raise is stored as `daily_loss_limit_pending_usd` with `daily_loss_limit_pending_from` (a day key). The trader promotes it at its first check of that day (`daily_limit.apply_pending`); the API shows the pending amount and its start day until then. Setting the amount back to the one in force cancels a pending raise; lowering also cancels it.
* **One-time default for existing live accounts** (`daily_limit.ensure_defaults`, run at startup by the API and by `main.py`, the same rule for every account): a live-authorised account with no amount gets 10 percent of its last stored account value (`account_day_equity.last_equity`), else 10 percent of its allocated capital, flagged `daily_loss_limit_is_default` until the customer sets an amount. An account with neither number stays without an amount and takes no new entry (switch on) until the customer sets one. Idempotent, never overwrites a customer's choice, logs one line per changed account (first 8 characters of the id and the amount, no personal data). A failure is one warning with the exception class only and never stops the service (for example before the migration has run).
* **Warning on the screen:** `one_trade_can_exceed_limit` is true when risk % x trading capital is above the amount (one trade can lose more than the limit; open trades keep their stop-loss).
* **Fail closed with no amount:** with the switch on, a live account without an amount takes no new entry (`daily_loss_limit_missing`, fixed customer message, one alert per hour).

### Behaviour

* Day: the calendar day in `ACCOUNT_DAY_TIMEZONE` (default `Africa/Lagos`), 00:00 to 23:59 local. Not a rolling 24 hours. The pause ends by itself at the next local midnight and nothing releases it earlier. The pause starts from `daily_loss_hit(start_equity, equity, limit_usd)`: a hit when the loss in dollars is at least the amount (1e-9 tolerance). The per-strategy daily loss guard uses the UTC day and is unchanged; the two boundaries differ by one hour for Lagos.
* Equity (realised plus unrealised): Spot is the total quote balance (free plus locked) plus each open bot position at quantity times mark price; other coins on the account are ignored. Futures is `info["totalMarginBalance"]` (wallet balance plus unrealised profit) from the same balance read. In ccxt 4.5.88 (the pinned version) `info` is the raw reply of Binance's account endpoint (`fapiPrivateV3GetAccount`), whose documented sample reply carries `totalMarginBalance` as a decimal string; this was checked against ccxt's source and that sample, NOT against a live reply. A missing field, a non-numeric or non-finite value, or a value that is zero or negative makes the answer "unreadable" (a zero cannot be a day start); it is never rebuilt from other fields. For Spot, an open position in a state other than open, protecting or closing (pending, attention) cannot be valued and also makes the reading unreadable.
* The sample and the pause check run once at the end of EVERY normal cycle of a live account that has an exchange client, whichever way the cycle ended (idle Auto scan, withdrawal block, no market data, multi-trade path, an unhealthy or open trade, the plain end), not only when a signal tries to enter (B1b). It is at most one balance read per account per cycle: the entry gate and the tick share the same reading. It does not run after an exception, for a paper account, or when there is no client (no linked notification channel, no usable credentials). A failed read logs `could not record an equity sample this cycle` once an hour per account and the cycle carries on. When the limit is crossed the tick writes the pause itself, so new entries stay blocked until 00:00 Lagos even with no signal; open trades are never touched.
* Fail closed: an unreadable or malformed equity, or an invalid time zone name (or a server without that tz database), blocks new entries and alerts. It is a refusal, not a recorded loss.
* Day-start equity is stored in `account_day_equity` (one row per account and local day), so a restart mid-day does not reset it. Each cycle of a live account stores a sample. A new day starts from the previous day's last sample if it was taken within one hour before midnight; otherwise from the first read of the day, flagged `approximate`. A day-start never moves up with equity.
* Blocks NEW entries only. Open trades keep their stops and strategy exits (tested: an exit runs during the loss).
* Audit: one row per account and day in `account_loss_pauses` (start equity, equity at hit, loss, limit, zone), one decision-log row per refused signal (`account_daily_loss_pause`, `account_equity_unreadable`, `account_day_timezone_invalid`), one customer alert when the pause starts. The alert states the amount lost today, "no new trades until midnight Lagos time" and, when the total stop's reference value is known, the total loss so far against it. The audit row's `limit_usd` is the amount in force; `limit_pct` is that amount as a percent of the day-start value.
* Known limit: a deposit or withdrawal you make during the day moves equity. A withdrawal looks like a loss (fails safe). A deposit can hide one. The keys are trade-only, so the bot never moves money. There is no adjustment command yet (planned, not built).
* The daily limit does NOT scale with an account's risk per trade. With a risk setting above the amount, one stop-out can already exceed it, so the pause then allows at most one losing trade per Lagos day; it never closes an open trade.
* Not a cumulative stop: it resets every day. A cumulative stop from the pilot start is a separate item.

## 2. Futures ceiling (`FUTURES_MAX_LEVERAGE`)

With a value above 0 (the owner sets 5), a new live Futures entry is refused when the leverage Binance reports for the pair is above the value, or the margin mode is not `isolated` (cross, or not reported). The bot only READS leverage and margin mode; it never sets either, and no confidence-based switching exists. The refusal uses a fixed customer message, a decision-log row (`futures_leverage_above_ceiling`, `futures_margin_not_isolated`) and the existing alert de-duplication (`PROTECTION_ALERT_REPEAT_HOURS`, default 6 hours). Spot is never affected.

Interaction with the pre-entry protection check (`PROTECTION_PRECHECK_MODE`): the ceiling runs first and needs no exchange call beyond the leverage read that was already there. The pre-entry check then runs unchanged and judges the stop against the liquidation price. It stays the second line: a leverage under the ceiling can still be refused by it (tested). `PRECHECK_MAX_LEVERAGE` (125) stays a plausibility bound on the value read; it is not the ceiling. For the pilot the owner should set `PROTECTION_PRECHECK_MODE=enforce`; the code default is `observe`, which blocks nothing.

## Owner steps (the owner runs every one; nothing here is done by the code)

1. Check no live trade is open: `python -m mba_bot.restart_gate` (exit 0 = clear; exit 3 = do NOT stop the service; exit 2 = unreadable, do not stop).
2. Stop the service.
3. Back up the database.
4. `alembic upgrade head` (applies `a8d2f6c1e3b7`: two new tables; and, for the dollar limit, `e3b6c8a1d5f2`: four columns on `trading_accounts` and `limit_usd` on `account_loss_pauses`). It must run before the new code starts: the startup default step and the models expect the columns.
5. Deploy the code.
6. Start the service. Check health and the journal. Both switches are still off.
   After any deploy of B1b, and any time you want to confirm the equity reading works, run `python -m mba_bot.equity_probe` from the app directory (read-only: it opens the database `query_only`, places no order, and prints for each live account only the id, the market and `equity=<2 decimals>` or `FAILED <class>`; never keys, per-asset balances or exchange text). Classes: `balance_call_failed`, `balance_malformed`, `margin_balance_missing`, `equity_not_positive`, `quote_balance_missing`, `position_mark_invalid`, `position_state_unknown`, `no_credentials`, `client_build_failed`, `unexpected_error`. Exit 0 all read, 2 a failure, 3 no live account. It makes Binance GET requests (the account endpoint, a ticker per open Spot position, ccxt's public market-data load).
7. Enable one switch at a time, each with its own restart (restart gate first, never restart with a live trade open): `ACCOUNT_DAY_TIMEZONE=Africa/Lagos` and `ACCOUNT_DAILY_LOSS_LIMIT=true` (if `ACCOUNT_DAILY_LOSS_PCT` is in the environment file, remove it: it is ignored, so leaving it would only mislead); then `FUTURES_MAX_LEVERAGE=5` (set leverage and isolated margin on Binance by hand first).
8. Watch the decision log for the reason codes above.

Rollback: remove the line, run the restart gate, restart. `alembic downgrade d2a5b9c7e1f4` drops the dollar-limit columns (the amounts are lost; customers must set them again before live trading); `alembic downgrade f3c8a1d6e2b9` also drops the two pause tables (the day-start references and pause audit rows are lost; nothing else changes). Turning the old percent pause back on would need the earlier code: this change removes it.

## NOT verified

* The one-time default on the owner's real database: the number it would pick depends on the last stored sample, which was not read. Check it with `python -m mba_bot.pilot_status` after the first restart, before turning the switch on.
* The customer screens (PR B).

* Binance: nothing was run against it. That ccxt's Futures `fetch_balance` carries `info.totalMarginBalance` as read here is an assumption (the pause blocks entries if it is absent).
* That the VPS has a tz database containing `Africa/Lagos` (the pause blocks entries if not).
* That one extra balance read per live account per cycle fits the Binance request weight budget (not measured).
* Gaps: the pause cannot see a loss that happens between the last sample and the next read, and it does not close anything.
* The fake exchange proves control flow only.
