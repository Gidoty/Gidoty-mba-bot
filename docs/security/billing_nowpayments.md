# NOWPayments (USDT on BSC) subscriptions, Stage 2 of the billing design

Status: BUILT, tested offline against a fake NOWPayments, NOT deployed, never run against NOWPayments. Three switches, all default OFF.
With them off: both new routes answer 404, no NOWPayments call is made, no row is written, and every existing route is unchanged.
No migration: `billing_payments`, `subscriptions` and `billing_notices` already hold every field (`billing_notices` gets one new kind).

## Switches and settings
| Variable | Default | Meaning |
|---|---|---|
| SUBSCRIPTION_BILLING_ENABLED | off | Master switch (Stage 0 to 3). |
| NOWPAYMENTS_ENABLED | off | Off: `POST /api/billing/crypto/initialize` and `POST /api/billing/nowpayments/ipn` answer 404. |
| NOWPAYMENTS_IPN_MODE | off | `off` ignore (answer 200), `observe` verify and log a MASKED verdict and write nothing, `enforce` apply. Anything else counts as off. |
| NOWPAYMENTS_API_KEY | unset | The owner types it into the server `.env` himself. Never in git, logs, chat or a message. Unset: checkout answers 503. |
| NOWPAYMENTS_IPN_SECRET | unset | Generated by the owner in the NOWPayments dashboard, typed into `.env` by him. Unset: enforce answers 503, observe answers 200 "no_secret". |
| NOWPAYMENTS_PAY_CURRENCY | unset | `usdtbsc` (the probe's answer). Unset: checkout answers 503. |
| NOWPAYMENTS_IPN_URL | unset | The public address of the IPN route, sent with each invoice. Unset: checkout answers 503. |
| NOWPAYMENTS_PRICE_USD | 10 | Price in USD. A malformed, zero or negative value counts as 10. |
| NOWPAYMENTS_UNDERPAY_TOLERANCE_PCT | 1.0 | Decision D8. A malformed or out-of-range (not 0 to 10) value counts as 1.0. |
The API key and IPN secret are registered with the log redaction. Rollback: unset NOWPAYMENTS_ENABLED (or set the mode to off) and restart. Rows stay and are ignored.

## Flow
1. **Checkout** `POST /api/billing/crypto/initialize` (logged-in customer). Refused (409) for lifetime customers, for a running card subscription (one channel at a time), and when a crypto period still has more than 7 days to run. Allowed with no subscription, while a period ends within 7 days, in grace, and when expired. At most 3 unpaid invoices per customer per 24 hours. The minimum payment is read from NOWPayments at run time (`fiat_equivalent`); if it is above the price the customer is told to pay by card, if it cannot be read checkout goes on, and if NOWPayments refuses the invoice the customer gets a fixed message and the row is marked failed. One `billing_payments` row (`mbacrypto_<24 hex>`, USD 10.00, pending) is COMMITTED before the invoice is requested, so no write lock is held during the call. The invoice: USD 10, `usdtbsc`, `is_fee_paid_by_user` false, `is_fixed_rate` false, our reference as `order_id`, the IPN URL, success and cancel URL = the dashboard. HTTP 200 and 201 are both success. The link is returned only if it is `https` on a `nowpayments.io` host.
2. **IPN** `POST /api/billing/nowpayments/ipn`: signature over the raw bytes first (below). The body is a TRIGGER: only `payment_id` is taken from it. The payment is re-read from NOWPayments and that record decides.
3. **Ladder.** The record is matched to OUR invoice by `order_id` (never by e-mail, address or amount), then checked for price (USD 10.00, exactly), price currency (usd) and asset (`usdtbsc`). A `parent_payment_id` (a repeated deposit) is never applied.

| NOWPayments status | billing_payments | Access | Owner alert |
|---|---|---|---|
| waiting, confirming, confirmed, sending | pending (nothing written) | none | no |
| finished, amount rule passes | paid | YES, one month | only if overpaid by more than 5 percent |
| finished, amount rule fails | underpaid | none | yes |
| partially_paid | underpaid | none | yes |
| failed | failed | none | yes |
| expired | expired | none | no |
| refunded (UNVERIFIED: not in the PDF's status list) | refunded | never revoked | yes |
| any other status | unchanged | none | yes |
Amount rule: `usd_value = price_amount * actually_paid / pay_amount` (the invoice's own rate, so no live rate is needed); granted if `usd_value >= 10 * (1 - 1 percent)`. The NOWPayments fee is the owner's, so it is never subtracted from the customer's payment. Overpayment grants ONE period and alerts; nothing is refunded automatically.
4. **Answers.** 200 for every final outcome (applied, duplicate, rejected, ignored, pending). 503 only when NOWPayments could not be asked (nothing was written), so it sends the notification again. 400 for a bad or missing signature in enforce mode, before anything is read.
5. **Replay protection.** `payment_events` key `nowpayments:<payment_id>:<status>` plus the unique `billing_payments` reference. A replay answers `duplicate`. A second, different finished payment for an invoice that is already paid is alerted and not applied. A late `waiting`, `failed` or `expired` never downgrades a paid invoice. A partial payment can still be topped up to `finished`.
6. **Atomicity.** The writes of one IPN start an explicit transaction first (the same reason as for Paystack: with pysqlite a row written inside a savepoint would otherwise survive a later error). A failure halfway rolls everything back; the redelivery then goes through.
7. **No write lock across a wait.** Every read (NOWPayments, Paystack) happens before the writes; Telegram alerts go out after the commit.

## The monthly period
No provider date exists, so the period is computed in ONE place, `billing/periods.py` (`add_months`, UTC, calendar months): new end = anchor plus one month, same day and time, clamped to the last day of a shorter month (31 Jan becomes 28 Feb, 29 Feb in a leap year; 31 Mar becomes 30 Apr). Anchor (decision D9): the current period end if the customer pays before it or inside the grace window, otherwise the moment the payment is applied. Paying early stacks; paying late in the grace window does not shift the period later. Known drift: a run that starts on the 29th to 31st keeps the shorter date afterwards (up to 3 days once). The Paystack path never uses `add_months`; a test checks that.

## Reminders and the banner
Through the existing notices module (once per period, Telegram if linked, banner): 3 days before the period end ("period_end_soon"), and when the period has ended unpaid and the 5-day grace window is open ("period_ended", new kind; crypto has no failure event, so the end of the period is the trigger). Both say access continues for the grace period and the banner has a "Pay now" button that calls the crypto route (it is allowed from 7 days before the end). The Paystack banner is unchanged.

## Card to crypto
A crypto payment in grace on a row that was a card subscription changes the row to crypto. If the old Paystack subscription is failed (`attention`) or due and unpaid, it is cancelled with its own stored token (the existing superseded-subscription step); a good one is never cancelled; if Paystack cannot be asked or the cancel fails, the payment still applies and the owner is alerted. A crypto payment while a card period is running is recorded as paid but NOT applied, and the owner is alerted.

## Signature (UNVERIFIED against a real IPN)
Header `x-nowpayments-sig`: HMAC-SHA512 (hex) of the body with the IPN secret. The PDF says to sort the keys, nested objects too, serialise, and sign. It does not say how numbers, separators or non-ASCII are written, so 16 equivalent serialisations are tried and the one that matched is logged (observe mode). Variants: nested keys sorted or only the top level (the common JavaScript idiom with a replacer array sorts only the top level), compact or spaced separators, UTF-8 or `\u` escapes, numbers as the sender wrote them or JavaScript style (`10.0` becomes `10`, `1e-7` stays `1e-7`). Numbers are kept as their original text, so no float round trip changes them. A forger without the secret cannot produce any of the 16. A signature that matches none of them is refused (enforce) or logged (observe).

## The payment record: the fields we rely on (CHECK THESE against one real payment)
`GET /v1/payment/{payment_id}` is not in the part of the PDF we read and the probe cannot call it. Nothing about its shape is assumed beyond these field names. The object may be the body itself or sit under `data`. Numbers may be numbers or strings. Status is lower-cased.
| Field | Used for | If missing or odd |
|---|---|---|
| `payment_id` | naming the payment, replay key, stored as `provider_payment_id` | the notification is ignored |
| `payment_status` | the ladder | unreadable: nothing granted, owner alerted |
| `order_id` | finding OUR invoice | no match: ignored (and alerted if it names no invoice of ours) |
| `price_amount` | must equal the invoice price (USD 10.00) | unreadable or rejected, nothing granted |
| `price_currency` | must be `usd` | unreadable or rejected |
| `pay_currency` | must equal NOWPAYMENTS_PAY_CURRENCY (`usdtbsc`) | unreadable or rejected (a wrong asset is alerted) |
| `pay_amount` | the invoice's own rate in the amount rule | a `finished` payment is unreadable: nothing granted |
| `actually_paid` | the amount rule | a `finished` payment is unreadable: nothing granted |
| `parent_payment_id` (optional) | a repeated deposit is never applied | treated as absent |
Not used: `outcome_amount`, `fee`, `pay_address`, `purchase_id`, any amount field in USD other than `price_amount`. The pay address and invoice link are never logged or stored.

## Observe mode, and how to compare with a real payment
In `observe` the handler does everything except write. For each notification it logs one INFO line from `mba_bot.billing.nowpayments`:
`nowpayments ipn[observe]: sig=<variant or INVALID> status=<status> payment=...<last 4> order=...<last 6> asset=<code> paid=<actually_paid> of=<pay_amount> usd=<value> verdict=<kind> reason=<code> fields_missing=<list or ->`
The owner reads it after one real payment and checks: `sig` names a variant (not INVALID), `fields_missing=-`, `verdict=apply`, `usd` is about 10. No body, secret, address, link or e-mail is logged. Only then is the mode changed to `enforce`.

## Owner steps (the owner does all of these; none needs a secret in chat)
1. In the NOWPayments dashboard generate the IPN secret (Payment Settings, place UNVERIFIED). Type it and the API key into the server `.env` yourself (`NOWPAYMENTS_API_KEY`, `NOWPAYMENTS_IPN_SECRET`), with `NOWPAYMENTS_PAY_CURRENCY=usdtbsc` and `NOWPAYMENTS_IPN_URL=https://<your host>/api/billing/nowpayments/ipn`.
2. Ask `partners@nowpayments.io` (from the account e-mail) for the list of IP addresses NOWPayments sends notifications from. Add a Cloudflare custom rule: URI path equals `/api/billing/nowpayments/ipn` and source IP in that list, action Skip (managed challenge, bot fight, rate limiting). Do NOT add a block rule for other addresses: a stale list would silently stop payments. Check that Paystack's webhook path is not challenged either.
3. Back up, deploy with `NOWPAYMENTS_ENABLED` and the master switch OFF, check health. Then set `NOWPAYMENTS_ENABLED=true`, `NOWPAYMENTS_IPN_MODE=observe`, restart. One switch at a time.
4. First real small payment: sign up a test customer, press Pay now, pay the invoice from your own wallet. Read the `ipn[observe]` lines. Send the sanitised lines back. If `sig=INVALID`, nothing is lost: observe writes nothing; we add the serialisation your payment shows.
5. Only after the comparison, set `NOWPAYMENTS_IPN_MODE=enforce`, restart, and make a second small payment; the customer must become entitled, `billing_payments` shows `paid` and the period end is one month on. Keep rollback ready (mode off, or `NOWPAYMENTS_ENABLED` off).

## What the offline tests cannot prove (UNVERIFIED)
* That NOWPayments signs as one of the 16 serialisations (the tests sign with an independent implementation of the PDF's description).
* The real IPN body, the real shape of `GET /v1/payment/{payment_id}` (every body in the tests is invented from memory), whether `refunded` exists, the meaning of `confirmed` versus `sending`, and how an expired invoice reads.
* NOWPayments' retry behaviour, timing, rate limits, the live fee, and the minimum amount (checked at run time, never reported).
* Cloudflare: whether the IPN is challenged before the skip rule exists.
* Anything about live mode or real wallets.
